## What was built

- **Air dock tab** (`MapDock::Air`, fifth tab). The panel is `map_air_tab` in `src/ui/air.rs`; `src/ui/map.rs` only dispatches to it.
  - SORTIES: a DPRK / NATO toggle, "Auto-fill from objectives" for that side (objectives and arrows; a second run adds nothing), and a compact list with name, target, weight, mode and ✖.
  - SHOW: four layer checkboxes.
  - TIMELINE: the shared `draw_slot_strip`.
  - Five tabs fit 288 px without the D35 "Refs" fallback, so D35 was not applied.
- **Map drawing.** `draw_map_air` runs right after `draw_map_objectives`. It paints the preview in `c::DPRK` / `c::NATO`:
  - dashed approach lines;
  - solid R rings and dashed inner rings;
  - spawn dots;
  - RTB dots with a thin line to the target.

  It records what it painted in `air_dock.drawn`.
- **Check cache.** `air_eval(plan, ctx)` keeps the issues, totals and preview for the last key. Both tabs, Map readiness and the drawing read it.
  - The key is a hash of the plan, every `AirContext` field, and the modified time of each user template file. The build re-reads those files (`assemble.rs` ≈170).
  - One change costs one cache miss, which is still two full builds (`validate` and `totals` each run `evaluate`) plus the preview.
- **Map readiness.** The check "Air Tasking plan is valid (see the Air Tasking tab)" appears only when `include_in_base_map` is ticked and the pool is not empty.
  - It fails on `AirIssue::blocks_build`. That is a new method in `airtask/mod.rs`; `export::blocking` now uses it, so the check and `build_air_packs` cannot drift apart.
  - The rail-only "no valid entry" issue shows as the orange note "Air Tasking has no valid entries and will be left out", under the dock tabs (visible on every dock tab). It does not block.
- **Generate.** `generate_front_file` calls `build_air_packs` when the plan is included and stops with its error. It adds `airtask::sidecar_paths` only when packs were built. With no plan, or the plan unticked, the output equals the baseline (tests).
- **Map undo.** The dock's Auto-fill and ✖ call `record_map_air_undo`, which puts `air: Some(plan)` in the `MapForces` snapshot. That differs from §6.2's "add the plan to MapForces": other Map undos keep `air: None`.
  - `settle_undo` counts the plan only when the snapshot holds it, like `lines`. So an Air Tasking edit made after a Map Clear keeps that Clear undo, and Ctrl Z does not revert the edit.
  - The unsaved-Map fingerprint (`map_fingerprint`) counts the plan only while it is included in the base map.
- **Load.** `load_base_map` clears the pool and keeps the library, categories, settings and seed. The status adds "Cleared N Air Tasking entries: a base map does not keep the pool." If the file had Air Tasking, the status is orange and carries the §7 text "Loaded map had Air Tasking; Generate will replace it with the current plan (removed if the plan is empty)." Load cannot be undone, as before.
- **Dead-code allows removed:**
  - `airtask/mod.rs` (the module allow and both `unused_imports`)
  - `in_theatre.rs`
  - `frontlines.rs` (`air_tasking_found`, now read by Load)
  - `placement.rs`
  - `template.rs`
  - `weapon_range.rs`

  Items that became warnings were handled this way:
  - `F80Cruise` and `f80_transit_s` left the `pub use` (they stay in `timing.rs`).
  - These became `#[cfg(test)]`, each with a reason comment: `AiRtbDecision::Enabled`, `CensusImpl::SameTick` (with its two match arms in `budget.rs`), `AirPreview::counts`, `ACCEPTED_SHAPES`, `threshold::OBJECT_LEFT` and `in_theatre::valid_on`.
  - Left as they are: the three `// P14 step 12` allows (spec ≈1609) and `trace.rs` (step 9T). `missionlog.rs` has none.
