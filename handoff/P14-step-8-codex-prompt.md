### A. Plan functions in `airtask` (backend, with unit tests)

New file `src/airtask/pool.rs`; `mod.rs` gets `mod pool;` and one `pub use pool::{…};` line, nothing else. Types derive `Debug, Clone, Copy, PartialEq` (plus `Eq` where possible):

- `pub enum TargetKind { Objective, Arrow }`
- `pub struct TargetChoice { pub kind: TargetKind, pub number: usize, pub side: AirSide, pub target: TargetRef }` — `number` is 1-based: for an objective, its place in that side's objective list (`ctx.east_objectives` = DPRK, `ctx.nato_objectives` = NATO); for an arrow, its place in `ctx.arrows`.
- `pub fn target_choices(ctx: &AirContext, side: AirSide) -> Vec<TargetChoice>` — that side's objectives, then the arrows whose side is `side`. Arrow side: `mapclip::point_north_of_front(ctx.front, tail.0, tail.1)`, north = DPRK (§5 "Target resolution").
- `pub fn resolve_target(target: &TargetRef, ctx: &AirContext) -> Option<TargetChoice>` — §5: an objective resolves to the nearest current objective of its side within 50 m; an arrow to an arrow with the same tip within 50 m (its side computed as above). `None` = orphaned.
- `pub enum EntryStatus { Ok, Orphaned, SideChanged, OutOfDate, MissingSortie }` and `pub fn entry_status(plan: &AirPlan, index: usize, ctx: &AirContext) -> EntryStatus` — `MissingSortie` when `sortie_id` is not in `plan.library`; `Orphaned` when the target does not resolve; `SideChanged` when it resolves to a side other than the sortie's; `OutOfDate` when `ctx.date` is outside the sortie's `valid` range (inclusive). Checked in that order. `enabled` does not change the status.
- `pub fn add_entry(plan: &mut AirPlan, entry: PoolEntry)` — appends; when the pool was empty before, sets `include_in_base_map = true` (D21).
- `pub fn auto_fill(plan: &mut AirPlan, ctx: &AirContext, side: AirSide) -> usize` — for each library sortie of `side` that is date-valid for `ctx.date`, and each `target_choices(ctx, side)`, adds `PoolEntry::new` (weight 5, mode Clock) unless an entry with that `sortie_id` already resolves to that same choice; returns how many it added. Running it twice adds nothing. Uses `add_entry`.
- `pub fn remove_library_item(plan: &mut AirPlan, index: usize) -> Result<usize, String>` — `Err` with a user-facing message for a `SortieSource::BuiltIn` item; otherwise removes it and every pool entry with its `sortie_id`, and returns how many entries went.

In `src/airtask/timing.rs`, next to `derived_timing` (and re-exported from `mod.rs` on the existing `pub use timing::{…}` line):
- `pub struct HardStop { pub clock_s: f64, pub zone_s: f64 }` and `pub fn hard_stop(sortie: &AirSortie, plan: &AirPlan) -> HardStop` — §4.3 `T_final`, the same arithmetic `assemble.rs` uses for `ShellSpec::final_time_s`: clock arrival = `schedule[side].arrive_min · 60`; zone arrival = `zone.spawn_dist_km · 1000 / (wp_speed_kmh / 3.6)`; each plus `attack_time_s + (stop.margin_min + stop.extension_min) · 60`. Tests pin §4.3: the F-80 HVAR built-in with defaults gives clock 2100 s; the F-51 ArmedRecon gives clock 2700 s; HVAR zone ≈ 1963.6 s.

Unit tests in `pool.rs` for every function above, each stating its literals (objective within / beyond 50 m, an arrow on each side of a simple two-point front, a moved front making `SideChanged`, a date outside a sourced range such as La-11 before 1953-04-15 with a hand-built `AirSortie`, auto-fill counts and idempotence, built-in removal refused, user removal taking its entries).
