What the frame shows

  • Left, Library (270 px). The built-ins and user templates as cards: side marker, name, role chips, planes, and the date badge for the Map date. A built-in cannot be removed, and the reason shows under the button, not only on hover.
  • Centre, Pool. One row per entry. Weight, Mode and Runs edit in the row. A grey row is switched off. An orphaned target or a failed date check turns the row's OK cell to ✖. Under the pool: the slot timeline and the plan check, both empty until step 7.
  • Right (304 px). The selected entry first (README §4), then Budget, Threshold, Schedule DPRK, Schedule NATO, Zone triggers, Hard stop and Output. Each section collapses to a one-line summary. Threshold's dwell, hold and inner radius come from airtask::derived_timing, which already works.
  • Works today: library (builtin_library, load_user_sortie), pool edits, undo, all settings, derived timing. Waits for step 7: the timeline, the plan check, the totals and Generate's output.
  • The Output section in the frame shows two of the four total rows; the build shows Copies, Aircraft, MCUs and Check zones.

Decisions, 2026-10-18

Each one was a place where plan §6.1 was unclear or conflicted with the redesign rules. You approved the mockup and every recommendation; they are recorded in decisions 0027 and 0028.

1

How does an entry get into the pool on this tab?

§6.1 gives the rail tab no way to add an entry. Only the Map dock's "Auto-fill from objectives" adds entries, and that is step 9, which waits for the upstream merge. Until then the pool could not be filled, and the step 8 tests that need an entry could only set it in code.

Decided: "Add to pool" on the selected library card, with a target list of that side's Map objectives and arrows; and "Auto-fill from objectives" in the pool header. The auto-fill rule is plan logic, so it goes into airtask as one public function that step 9's dock button calls too. Also, as its own step after the upstream merge (decision 0028): upstream's "+ Mission" CAP / Strike builder makes library sorties, and Map › Missions snap targets (tanks, truck routes, rail, ships, airbases, bridges, dams) become pool targets.

2

A nine-column pool table does not fit

At 1280 px the centre is about 534 px. §6.1's nine columns (Sortie, Side, Target, Weight, Mode, Runs, Heading, Valid, ✖) need more, and the redesign puts "the current selection first" in the right panel.

Decided: the side becomes the marker in the Sortie cell; Weight, Mode and Runs stay editable in the row; Heading override moves to the selected-entry block. Long names are cut with "…" and shown in full on hover.

3

Where is an entry switched on and off?

PoolEntry.enabled exists, but §6.1 gives it no control.

Decided: a checkbox in the first column. A switched-off row is grey and is left out of Generate.

4

Where do the slot timelines go?

§6.1 puts one strip inside each side's Schedule section, in the 304 px right panel, under eight fields.

Decided: one Slot timeline panel in the centre, under the pool, with both sides on one 0–3 h axis. It uses the same draw helper step 9's dock will use. The Schedule sections keep only their fields.

5

What should Generate do before step 7?

Today validate, totals, preview and build_air_packs return empty results. Wired as §6.1 says, readiness shows only the checks the UI can see, totals read 0, and Generate File would write an Air Tasking group with no sorties in it.

Decided: wire the tab to the real API now and change nothing at step 7. The step 8b tests that need step 7 are written now and marked #[ignore = "needs step 7"]; step 7 removes the marks. Nothing ships from this branch before step 7 lands.

6

What does Reset clear?

§6.1 adds a Reset confirmation but does not say what it keeps.

Decided: Reset empties the pool, restores every setting to its default and draws a new seed. It keeps the library, so user templates stay, the same way Template Builder's Reset keeps the catalog. Ctrl Z undoes it.

7

Removing a user template that the pool uses

§6.1 does not say what happens to the pool entries of a removed library item.

Decided: they are removed with it, and one Ctrl Z restores the template and its entries. The undo label names both, for example "Removed La11_Night_Intruder and 1 entry".

8

What goes next to the title?

Other tabs show the file being edited. The plan is not a file.

Decided: the Map date and the entry count, for example "Map date 15 Sep 1950 · 7 entries", because the date decides which sorties are valid.

9

The hard-stop time per entry

§4.4 wants each entry's hard stop (arrival + attack time + margin + extension) in a tooltip. No public airtask function returns it, and the UI must not compute it.

Decided: add one small public function next to derived_timing in airtask/timing.rs, with a test, as part of this step, and show the value in the selected-entry block.

10

Section style

§6.1 says every section uses shell::section_title; the redesign says settings sections collapse to a one-line summary (shell::settings_section).

Decided: settings_section, with Budget, Threshold and Output open at first. The 28 px guard test opens every section.

Facts to know, no decision needed

  • Every built-in's models (F-80C, F-51D, Yak-9P, Il-10) have no sourced date in in_theatre.rs, so they are valid for any date in the war, even though their names carry dates such as "Jun–Jul 1950". Only La-11 and MiG-15bis have sourced dates today.
  • Objectives and arrows are named by their order on the Map ("Objective 2", "Arrow 1"). The Map does not draw those numbers yet; step 9 draws the targets.
  • The tab goes in a new file, src/ui/air.rs, with small hooks in ui.rs, shell.rs and help.rs, so the upstream merge (which split ui.rs into src/ui/*.rs) conflicts as little as possible.
